    req_start, req_end = parse_time_range(time_slot)

## II. Debugging Case Study (10 Points)

### Problem Description

During testing, the agent consistently reported "Kín lịch" (fully booked) even when rooms were clearly available in the dataset. This caused the agent to loop — repeatedly suggesting the user change their time slot without ever finding a valid room.

```
[ACTION INPUT]: {"time_slot": "08:00-12:00"}
[OBSERVATION]: Kín lịch: Không có phòng trống trong khung giờ này.
[ACTION INPUT]: {"time_slot": "08:00-12:00"}   ← same input, same wrong result
```

### Log Source

Observed during manual testing of `check_available.py` with inputs generated by the LLM. The LLM sometimes produced `"08:00-12:00"` (no spaces) while the dataset stored `"08:00 - 12:00"` (with spaces around the dash).

### Diagnosis

**Root cause: String comparison instead of numeric comparison.**

The original implementation used direct string matching:

```python
# BROKEN: fails if format differs by whitespace
if time_slot in room_data["availability"][day]:
    return True
```

When the LLM generated `"08:00-12:00"` and the dataset contained `"08:00 - 12:00"`, the comparison failed silently — returning "no rooms available" even when rooms were free.

This is a classic LLM integration pitfall: the model cannot guarantee exact string format consistency, so the tool must be format-tolerant.

### Solution

Replaced string comparison with integer arithmetic on minutes:

```python
def parse_time_range(time_str: str) -> tuple[int, int]:
    """Convert 'HH:MM - HH:MM' or 'HH:MM-HH:MM' to (start_minutes, end_minutes)."""
    # Remove all spaces, split on dash
    clean = time_str.replace(" ", "")
    start_str, end_str = clean.split("-", 1)
    start = int(start_str[:2]) * 60 + int(start_str[3:5])
    end   = int(end_str[:2])   * 60 + int(end_str[3:5])
    return start, end

# FIXED: numeric overlap check
req_start, req_end = parse_time_range(requested_slot)
avail_start, avail_end = parse_time_range(available_slot)
if req_start >= avail_start and req_end <= avail_end:
    available_rooms.append(room_info)
```

After this fix, the agent correctly identified available rooms regardless of whitespace formatting in the LLM's output.

## III. Personal Insights: Chatbot vs ReAct (10 Points)

### 1. Reasoning — The Thought Block

The chatbot answers by pattern-matching against training data — it "knows" what a classroom recommendation should look like, but it doesn't *verify* anything. The `Thought` block in ReAct forces the model to externalize its reasoning step by step:

- **Chatbot**: "You need a room for 30 people → here are some rooms" (one shot, no verification)
- **ReAct Agent**: "I need to search first → I got results → now I need to check if they're free → A101 is taken → try A301 → A301 is free → recommend A301"

The Thought block creates an audit trail. When the agent fails, you can read the trace and see exactly where the reasoning broke down — something impossible with a black-box chatbot response.

### 2. Reliability — When Agent Performs Worse

| Scenario | Chatbot | ReAct Agent |
|----------|---------|-------------|
| Simple question ("Phòng nào lớn nhất?") | ✅ Fast, sufficient | ❌ Wastes 2-3 tool calls |
| Weak local model (Phi-3-mini) | ✅ Returns something | ❌ Loops, hits max_steps |
| Tool format error (string mismatch) | ✅ Unaffected | ❌ Returns wrong results silently |
| Network/API down | ✅ Still responds | ❌ Completely fails |
| Multi-step with real data | ❌ Hallucinate | ✅ Grounded answer |

The agent's reliability is **bounded by its tools**. If a tool has a bug (like the string comparison issue I fixed), the agent will confidently produce wrong answers — and the user has no way to know. The chatbot at least fails in an obvious way (hallucination is detectable).

### 3. Observation — The Feedback Loop

The Observation step is what makes the agent fundamentally different from a chatbot. Each tool result updates the agent's "world model" for that session:

```
Action: check_availability("A101", "Mon 09:00")
Observation: Phòng A101 đã được đặt.          ← world model updated
Thought: A101 is taken, try A301.              ← reasoning adapts
Action: check_availability("A301", "Mon 09:00")
Observation: Phòng A301 còn trống.             ← confirmed by real data
Final Answer: Recommend A301.                  ← grounded conclusion
```

Without Observations, the chatbot is reasoning in a vacuum — it can only use what it learned during training, which may be months or years out of date. The Observation loop is what makes agents suitable for real-time, dynamic data.
